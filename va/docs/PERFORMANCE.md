# 系統效能量測與工程紀錄 — v7.2

## 量測方式與限制（請先讀這段，避免誤用數字）

> **版本說明：** 本文件保留 v7.2 開發階段的沙盒量測紀錄，屬於工程參考值，不是雲端正式環境 SLA，也不代表目前硬體／作業系統上的固定數字。正式部署前請重新量測。

- **量測環境**：本次量測在沙盒容器內以 `fastapi.testclient.TestClient`
  直接呼叫 ASGI app（無真實網路／TCP/TLS handshake 開銷，CPU 為容器
  共享核心），**不是**正式雲端部署（Azure App Service）環境下的量測，
  數字僅反映「API 本身的運算延遲」（特徵擷取＋模型推論／快取查找），
  不包含真實網路往返時間（RTT）、反向代理、TLS handshake 等正式部署
  才會有的額外開銷。正式口試／論文中請明確註明這個差異，不要直接宣稱
  這是「使用者實際感受到的延遲」。
- 量測時**刻意停用了 `security.RateLimiter`**：v7.2 新增了 `/predict`
  （120 次/分）與 `/predict/batch`（30 次/分）的限流（見下方「新增限流
  對效能測試的影響」），若不停用，批次量測在幾十次請求後會開始被
  429 快速拒絕，量到的會是「限流器拒絕的時間」而非「真正算完一次
  預測要多久」，兩者差兩個數量級，務必注意這個陷阱。
- 「冷快取」每次都用全新、從未出現過的網址，確保不會命中
  `prediction_cache`；「熱快取」固定打同一個網址。
- 以下皆為單一行程、循序量測（非多工並發壓測），**不是**
  `requests/sec` 壓力測試的吞吐量數字，而是單次請求延遲分布。

## 一、API 延遲（本次實測）

| 測試項目 | n | Mean | P50 | P95 | P99 | Min | Max |
|---|---:|---:|---:|---:|---:|---:|---:|
| `/predict` 冷快取 | 100 | 7.36 ms | 5.54 ms | 6.72 ms | 7.48 ms | 5.09 ms | 173.24 ms* |
| `/predict` 熱快取 | 100 | 0.59 ms | 0.58 ms | 0.68 ms | 0.78 ms | 0.46 ms | 0.81 ms |
| `/predict/batch` 10 筆（compact） | 40 | 46.73 ms | 46.41 ms | 50.82 ms | 53.72 ms | 42.46 ms | 53.72 ms |
| `/predict/batch` 50 筆（compact，上限） | 40 | 235.82 ms | 232.12 ms | 268.88 ms | 307.47 ms | 214.17 ms | 307.47 ms |
| `deep_scan=false` | 60 | 6.09 ms | 6.15 ms | 6.69 ms | 6.90 ms | 5.39 ms | 6.94 ms |
| `deep_scan=true`（沙盒無對外網路，落入逾時/失敗路徑） | 20 | 8.35 ms | 8.32 ms | 8.98 ms | 9.26 ms | 7.53 ms | 9.26 ms |

\* 冷快取 max 173ms 為首批請求中偶發的一次離群值（推測為 Python
GC／JIT warm-up 或 `lru_cache` 首次填充造成），P95／P99 已不受影響，
可視為單次異常值而非常態延遲。

**可讀出的結論**：

1. **熱快取命中時延遲 < 1ms**，TTLCache 的「高頻安全網域跳過模型
   推論」設計確實有效，相較冷快取約快 10～12 倍。
2. **batch 50 筆（約 235ms）約為 batch 10 筆（約 47ms）的 5 倍**，
   接近線性隨筆數增長（50/10=5），代表批次處理沒有明顯的額外開銷，
   單筆攤提成本穩定。以此估算單筆攤提延遲約 4.7ms／筆，與單筆
   `/predict` 冷快取的 5.5ms 相近，合理。
3. `deep_scan` 的開銷在「抓取失敗／逾時」路徑下約多 2ms（8.35ms vs
   6.09ms），這是**最保守**的情境（本次沒有測到「成功抓到網頁＋跑完
   BERT」的真實開銷，因為容器沒有對外網路、且 `ENABLE_BERT` 預設
   關閉）；若要量測完整 deep_scan 開銷，需要在可連外網的環境、且安裝
   `torch`/`transformers` 並設定 `TRUTHMARK_ENABLE_BERT=1` 後重測，
   論文中請明確註明目前數字不含這個情境。

## 三、新增限流對效能測試的影響（開發過程中的真實教訓）

v7.2 在替 `/predict`、`/predict/batch` 補上限流時，第一次量測（未停用
限流器）得到的 batch 50 筆數字是 0.63ms——明顯不合理。排查後發現是
因為同一支測試腳本連續呼叫同一條路由超過限流門檻，後段請求被 429
瞬間拒絕（根本沒有進入特徵擷取／模型推論），才會「快得不像話」。這個
過程本身就是個值得寫進論文「系統限效能量測」小節的真實案例：**效能
測試必須考慮限流等中介機制對量測結果的干擾**，這是本次實際踩過的坑，
修正方式見上方「量測方式與限制」。

## 四、尚未做、不在本次範圍內的量測

- **requests/sec 吞吐量壓力測試**（例如用 `locust`／`wrk` 對正式部署
  環境做多工併發壓測）：需要在可長時間佔用網路與 CPU 資源的環境執行，
  不適合在本次沙盒內進行，建議部署到 Azure 後用 `locust` 另外測。
- **真實網路往返時間（RTT）**：需要從瀏覽器擴充套件實際連到雲端後端
  量測，見 `docs/EXTENSION_E2E_TESTING.md`。
- **`deep_scan=true` 成功抓到頁面＋完整 BERT 推論的延遲**：需要可連外
  網的環境並啟用 `TRUTHMARK_ENABLE_BERT=1`，見上方說明。
